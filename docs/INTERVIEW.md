# 面试追问与答法

每个问题给三件事：**一句话结论 → 展开要点 → 别踩的坑**。

---

## 1. 两个学生同时抢最后一个名额，会不会超卖？

**结论：不会。判断和扣减在同一条 SQL 里完成。**

```sql
UPDATE edu_offering SET enrolled = enrolled + 1
 WHERE id = ? AND enrolled < capacity AND status = 1
```

- 返回值是受影响行数：1 表示抢到，0 表示已满，直接抛业务异常；
- InnoDB 对同一行加排他锁，两个事务串行执行，第二个看到的 `enrolled` 已经是 31 之前的值；
- 不会出现「先 SELECT 查到 29 < 30，再 UPDATE」中间被别人插队的窗口。

**坑**：不要答「加了 synchronized」。那是单机锁，多实例部署就失效，而且把并发压成串行，接口吞吐会掉。

---

## 2. 权限只在前端隐藏按钮，算做了权限吗？

**结论：不算，必须服务端拦。**

- 前端隐藏只是体验，改个 localStorage 里的 perms 或直接调接口就绕过了；
- 真正的拦截在 `@PreAuthorize("hasAuthority('edu:course:add')")`，Spring Security 在方法调用前比对 `Authentication` 里的 authorities；
- 菜单、按钮、接口读的是同一份 `sys_menu.perm`，改授权只改一处。

测试里专门验证了：学生和教师调 `GET /users` 都是 403（`AuthAndPermissionTest`）。

**坑**：不要说「前端做了就够」。这是安全题，答错直接减分。

---

## 3. JWT 怎么注销？用户被停用了旧令牌还能用吗？

**结论：无状态令牌没法「作废」，只能靠短 TTL + 服务端黑名单。**

- 本项目：TTL 8 小时，注销只是前端删掉本地令牌（`POST /auth/logout` 保留但不做服务端动作）；
- 用户被停用：`sys_user.status = 0` 后**已签发的令牌在有效期内仍可用**，这是已知缺口；
- 生产做法：Redis 存 `jti` 黑名单（登出/停用时写入，TTL 与令牌一致），每次请求校验一次。

**坑**：别说「JWT 天然安全」。它只是签名的，不能撤销，泄露后在过期前都有效。

---

## 4. 改了角色权限，为什么用户要重新登录？怎么改成立即生效？

**结论：因为权限点写在令牌里，签发时就固定了。**

- 现状：授权变更后，旧令牌仍带旧 perms，最长 8 小时后才自然失效；
- 改法：令牌里只放 `userId`，每个请求从 Redis 取 `perms`（`userId` 作 key），授权时 `DEL` 该 key；
- 取舍：从「零查询」变成「一次 Redis 读」，换来即时生效。没有 Redis 时退而求其次可以每次查库，但要配本地缓存。

这个取舍我写在了 `docs/DESIGN.md` 第 4 条，README 的局限里也挂了这句。

---

## 5. 时间冲突为什么不做成数据库约束？

**结论：区间重叠没法用唯一索引表达。**

- 唯一索引能挡「同一行重复」，挡不住「周一 1-2 节」和「周一 2-3 节」的重叠；
- PostgreSQL 有 `EXCLUDE USING gist (tsrange WITH &&)`，MySQL 没有；
- 另一条路是拆成「学生-节次」占用表，每节课一行，唯一索引兜底——但一个学生 8 门课要写几十行，退课、改时间都要同步维护，收益不抵复杂度。

**加分**：可以说清「如果课程时间固定不变、且节次粒度粗，占用表是可行的；这里时间可改，所以选应用层校验」。

---

## 6. 总评和绩点为什么不让前端算？

**结论：前端算等于把成绩交给浏览器改。**

- 总评 = 平时 × 30% + 考试 × 70%，绩点按 4.0 制分段，都在 `ScoreService`；
- 加权绩点用 SQL 聚合：`SUM(gpa * credit) / SUM(credit)`，不把整张成绩单拉到内存；
- 只有任课教师能录自己班的成绩，`ScoreService.save` 里校验 `offering.teacherId == 当前用户`。

---

## 7. 列表里要显示教师姓名、课程名，你怎么避免 N+1？

**结论：一次 JOIN 查完，或者批量查再在内存里拼。**

- 开课列表、成绩列表、课表都是注解 SQL 里 JOIN 出展示字段（`OfferingVO`、`ScoreVO`）；
- 用户列表的角色是另一张表，用 `WHERE user_id IN (...)` 一次取回，再按 userId 分组，避免每人查一次；
- 判断标准：接口里出现「循环里查库」就是 N+1 信号。

---

## 8. 为什么用 MyBatis-Plus，不用 JPA？

- 报表类查询（多表 JOIN、按条件拼 WHERE）用 SQL 更直接，JPA 的 Criteria/JPQL 反而绕；
- 单表 CRUD 用 `BaseMapper` + `LambdaQueryWrapper`，不用写 XML；
- 分页插件统一处理 `LIMIT`，也顺手限制了 `pageSize` 上限（200），防止前端传 99999 拖死库。

**坑**：不要说「MyBatis 比 JPA 快」。性能差异不在 ORM 本身，在于你能不能控制生成的 SQL。

---

## 9. 测试为什么跑 H2？能保证和 MySQL 一致吗？

**结论：不能完全保证，所以真实库也手工跑过。**

- H2 开 `MODE=MySQL`，同一份 `schema.sql` / `data.sql` 两边都能建；
- 只用两边都支持的语法：`LIMIT`、`CONCAT`、条件更新、`DECIMAL`；
- H2 的价值是「CI 里不需要起数据库，测试秒级可跑」；
- 风险点：索引行为、锁粒度、`ON DUPLICATE KEY` 这类 MySQL 专有语法都不能依赖。本项目没用。

---

## 10. 这个系统能扛多少并发？瓶颈在哪？

**结论：单机几十到几百 QPS 量级，瓶颈在热门课程那一行的锁。**

- 选课是「同一行更新」，热门课会在这行上排队；
- 读多写少的接口（课表、成绩、公告）没有这个问题；
- 上量方案：Redis 预扣名额 + MQ 异步落库 + 定时对账；
- 另一个瓶颈是 `sys_oper_log` 同步写入，量大时应该改成异步队列。

诚实说「没做过压测，这是我的估算」，比编一个 QPS 数字好。

---

## 11. 操作日志会不会拖慢接口？

- 同步插入一条记录，正常几毫秒；写入失败只 `warn`，不影响主流程（审计是旁路）；
- 参数截断到 900 字符，避免大 body 撑爆表；
- 量大时的改法：改成 `@Async` + 队列，或直接写文件交给日志系统采集。

---

## 12. 如果继续做，下一步做什么？

按优先级：

1. **Redis 名额预扣**：解决热门课锁竞争，也是最能体现「知道瓶颈在哪」的一步；
2. **权限缓存 + 即时失效**：补掉「改角色要重新登录」的体验缺口；
3. **排课**：现在时间是手工填的，加一个「按教师/班级/教室的空闲时段推荐」；
4. **审计归档**：`sys_oper_log` 按天分区或定期转冷存储；
5. **前端单测**：现在只有后端集成测试，交互逻辑没覆盖。
